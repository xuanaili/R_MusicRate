# 大版本功能规划工作流

> 从 BookRate 迁移（2026-08-10），适配 MusicRate。适用于构思/规划大版本功能、写进 ai/planning/ 版本规划的场景。

## 触发场景
用户提出"构思/规划一个大版本功能"、"判断可行性"、"写进 README 版本规划"；或涉及新模块、新表、架构决策时启用。此流程只**出方案 + 写规划文档（ai/planning/）**，不写实现代码。

## 流程（按序执行）

### 1. 需求解读 → README 对齐
- 先读 `README.md` 版本演进索引 + `ai/planning/` 目录列表，确认当前版本进度（已完成/进行中）与待做项（`ai/planning/` 有 v0.9 / v0.8.x 等版本文档，待办见 `BACKLOG.md`）
- 确认新版本号：已完成 v0.N → 新规划为 v0.N+1
- 拆解需求为：功能概述 / 数据需求 / 落点位置 / 需用户拍板的决策点

### 2. 现状盘点 → 只读落点文件
按 CLAUDE.md 目录结构定位，**只读"落点 + 直接依赖"文件**，用 Grep 精准定位后再小范围 Read，不冗余全量读取（见 token 优化工作流）：
- 前端落点：对应视图/组件（如 `AlbumDetail.vue`、`WebHome.vue` 的 Tab）
- 后端数据来源：对应 api 模块（评分→`score.py`、听后感→`review.py`、评论→`comment.py`…）
- 建表：`backend/utils/db.py`（确认字段，不假设存在）
- 路由注册：`backend/api/__init__.py`
- 配置：`backend/config.py`

### 3. 数据来源梳理 → 表格化
用表格列出需求所需数据，逐条确认路径通：
| 数据 | 存哪 | 现成 or 需新建 | 查询接口/字段 |
|------|------|--------------|--------------|
| … | … | … | … |

### 4. 可行性判断
- 给出明确结论：可行 / 不可行 / 有条件可行
- 列出关键难点（成本、跨表、安全、性能、外部依赖）与对策

### 5. 架构设计
- **新表**：表名 / 字段 / 用途（注意用户分表模式：`albums_{user_id}`）
- **后端接口**：路由 + body / 是否 `@login_required` / 限额
- **前端组件**：位置 / 复用哪个现有组件风格 / 显隐策略
- **安全与成本**：密钥只存后端、前端只存状态
- **上下文/数据组装**：如果功能要读大量数据，给出"静态背景 + 增量/按需 + 缓存"的分层方案

### 6. 决策确认（关键步骤，别跳过）
- 用 AskUserQuestion 或明确列出需要用户拍板的点（provider、密钥模式、显隐策略、默认值等）
- **不替用户做产品决策**，但每个点给推荐项
- 用户拍板后把结论固化进规划文档的"已定决策"表

### 7. 写入 `ai/planning/`（版本文档模板）
在 `ai/planning/` 新建 `v0.x_简短英文描述.md`（先读 `00_template.md`），结构固定：
- **功能概述**：一段话说清做什么
- **已定决策**：表格（决策点 / 结论）
- **架构设计**：数据如何组装
- **数据库表**：新增 N 张
- **后端接口**：路由清单
- **前端组件**：落点与样式
- **分阶段路线**：P0→P1→P2，每阶段一句话范围
- **难点与对策**
- **待做**：勾选清单（含上一版本遗留待做项）

历史版本文档状态标为"已完成"，原内容保留在 `ai/planning/`。

### 8. Git 提交
按 git 提交规范提交，说明修改内容。

### 9. 不写实现代码
规划结束 = `ai/planning/` 有 `v0.x_*.md` + README 版本演进索引已同步一行。实现等用户确认后，再按 `feature_development_workflow`（20260810）拆 P0 任务逐步落地。
